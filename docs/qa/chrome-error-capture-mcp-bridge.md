# Chrome 前端错误捕获与 Claude Code/MCP 桥接方案 QA

- **文档状态**：初版调研记录
- **资料来源**：用户提供的 Grok 方案建议
- **核验日期**：2026-08-19
- **适用范围**：评估“是否需要自研 Chrome 扩展 + 本地 MCP 桥接”这一方向，不等同于具体实现设计或生产可用性认证。

## 1. 结论

当前不应直接从零实现完整 Agent。更稳妥的路径是先验证 Chrome DevTools MCP 是否已经覆盖当前调试闭环；只有在错误结构化、源码关联、框架解析、隐私隔离或交互体验等方面存在明确缺口时，再实现一个范围受控的扩展与本地 MCP 桥接。

Grok 资料的核心判断基本合理，但其中“Console Catcher / Browser Runtime MCP”等第三方工具的具体能力、维护状态和兼容性没有在原资料中提供证据，不能直接作为已确认事实。

## 2. 证据等级说明

| 等级 | 含义 |
| --- | --- |
| 已确认 | 可由官方文档或当前项目事实直接支持 |
| 合理判断 | 基于工程经验的建议，仍需结合实际工作流验证 |
| 待验证 | 原资料提出但缺少足够证据，不能据此做技术承诺 |
| 不应直接采纳 | 表述过度绝对、范围不清或容易造成错误预期 |

## 3. 对 Grok 观点的核验

### 3.1 “大多数情况下没必要从零实现”——合理判断

该判断可作为默认策略，但不是普遍事实。Chrome DevTools MCP 已经提供浏览器调试和自动化能力，优先验证现有能力通常比并行维护扩展、桥接服务和 Agent 更省成本。

是否需要自研，取决于以下差距是否真实存在：

- 是否需要稳定、结构化的错误事件模型，而不只是调试工具返回的消息；
- 是否需要将堆栈位置自动映射到本地 Git 仓库文件；
- 是否需要针对 React、Vue、Svelte 等框架做特定解析；
- 是否需要自定义侧边栏、筛选、去重和“一键发送”体验；
- 是否要求错误数据完全留在本机，并能审计数据流向。

### 3.2 “现有 MCP 能覆盖捕获报错并交给 Claude Code”——部分已确认，部分待验证

已确认：

- Chrome DevTools MCP 暴露 Chrome DevTools 能力；
- 官方工具列表包含获取 console 消息/错误、查看网络请求等能力；
- Claude Code 支持连接本地 MCP Server，stdio 是官方支持的本地传输方式。

仍需验证：

- 具体 MCP 客户端是否能稳定连接目标浏览器实例；
- 页面加载前发生的错误是否能被完整捕获；
- 是否保留完整堆栈、source map 后位置和页面上下文；
- 错误是否能自动持久化、去重和按时间/页面筛选；
- “Console Catcher / Browser Runtime MCP”是否为当前可用、受维护且适配本项目的工具。

因此，不能把“核心需求已经完整覆盖”写成无条件结论，应改为“官方能力覆盖了重要基础能力，但闭环覆盖率需要在目标项目中实测”。

### 3.3 “极简插件 + 本地 MCP 桥接”——合理的候选架构

该架构的职责划分是合理的：扩展负责浏览器侧感知与收集，MCP Server 负责向 Claude Code 提供结构化上下文，代码修改仍由 Claude Code 在本地仓库中完成。

但它不是零成本方案，至少还需要明确：

- 扩展如何跨页面、跨 frame 捕获事件；
- content script 能捕获哪些错误，哪些必须通过 DevTools Protocol 或页面注入实现；
- 插件到本地服务的通信方式、来源校验和权限边界；
- 敏感 URL、请求头、页面文本和 DOM 摘要是否会被收集；
- MCP 工具是否只读，还是允许触发文件或命令操作。

### 3.4 “Manifest V3 + TypeScript + Vite/Plasmo + Node MCP”——技术选型建议

这些选型总体可行，但不是已验证的最佳组合：

- Manifest V3 是 Chrome 扩展的当前平台方向；
- TypeScript 适合维护事件模型和 MCP 数据协议；
- Vite 或 Plasmo 都可能降低扩展开发成本，但应根据项目是否需要框架约定、构建复杂度和调试体验选择；
- Node.js 适合快速实现本地 MCP Server；Rust/WASM 只有在性能剖析证明需要时再引入。

“可选 Rust WASM 做去重、堆栈解析”不应进入第一阶段。错误数量通常不是这类系统的首要瓶颈，引入 WASM 会增加构建、调试和跨环境维护成本。

### 3.5 “1–2 周可出可用版”——待验证，不作为承诺

工期高度依赖：

- 是否已有扩展脚手架和本地 MCP 经验；
- 是否只支持 console.error，还是还要覆盖 uncaught exception、rejection、网络错误和 iframe；
- 是否需要 source map、仓库关联、持久化和 UI；
- 是否需要 macOS/Windows/Linux 多平台验证。

在没有范围冻结和验收标准前，不应把“1–2 周”当作项目估算。

## 4. 推荐的最小验证闭环

先不开发自研扩展，使用官方 Chrome DevTools MCP 完成一次端到端验证：

1. 启动一个包含已知 `console.error`、未捕获异常和 Promise rejection 的测试页面；
2. 通过 Chrome DevTools MCP 读取 console 消息，记录是否包含时间、级别、文本和堆栈；
3. 触发一个已知网络失败，确认网络信息的粒度和敏感字段暴露情况；
4. 在 Claude Code 中通过 MCP 查询最新错误；
5. 检查 Claude Code 能否根据堆栈定位到本地仓库文件；
6. 记录缺口：捕获遗漏、上下文不足、去重困难、跨页面问题和人工操作成本；
7. 只有缺口明确且重复出现，才进入扩展 + 本地桥接的 MVP 设计。

## 5. 自研 MVP 的边界

若验证后仍需自研，第一版只实现以下闭环：

- 捕获 `console.error`、`window` 未捕获异常和 `unhandledrejection`；
- 保存页面 URL、标题、时间、错误级别、消息和可用堆栈；
- 提供最近错误列表和手动发送操作；
- 本地 MCP Server 提供只读的“获取最新错误”和“按页面/时间查询错误”工具；
- 默认不采集完整 DOM、不采集请求头、不自动执行修复命令；
- 通过显式配置限制本地服务监听范围和允许连接的扩展来源。

以下能力延后：自动源码关联、框架专用解析、网络请求全量采集、WASM 优化、内嵌 Agent、数字人 UI 和自动修复按钮。

## 6. 风险与边界

### 隐私

错误消息、URL、DOM 摘要、请求参数和堆栈可能包含令牌、用户数据或内部路径。应采用最小采集、敏感字段脱敏和本地存储策略，不应仅凭“本地 MCP”就宣称绝对隐私安全。

### 安全

本地桥接服务仍是本机攻击面。必须考虑端口暴露、跨源请求、扩展 ID 校验、消息大小限制和工具权限隔离。MCP Server 若提供写文件或执行命令能力，应单独设计授权和确认机制。

### 捕获完整性

content script、页面注入、DevTools Protocol 的可见范围不同。跨域 iframe、页面早期错误、扩展不可注入页面和 source map 缺失都会造成信息不完整。

### 诊断正确性

浏览器错误只能说明运行时现象，不能自动证明根因。Claude Code 修改代码前仍需结合仓库代码、复现步骤、测试和人工审阅。

## 7. 决策规则

| 观察结果 | 建议 |
| --- | --- |
| 官方 MCP 已能读取所需错误，且人工查询成本可接受 | 不自研，先固化使用流程 |
| 能读取错误，但无法稳定关联本地源码 | 先做堆栈/source map 关联实验，再决定是否扩展 |
| 需要统一收集、去重、筛选和持久化 | 开发小型采集层或扩展，不引入 Agent |
| 需要完全自定义 UI 或工作流 | 在 MVP 中加入 Side Panel，但保持 MCP 只读 |
| 需要数据完全本地化 | 设计数据流和权限模型后再实现，不能只依赖工具名称判断 |
| 想在浏览器内嵌完整 Agent | 除非有明确产品需求，否则不建议作为第一阶段 |

## 8. 待补充资料

- 目标项目使用的前端框架、构建工具和 source map 配置；
- 需要捕获的错误类型和可接受的遗漏范围；
- 是否需要网络请求、DOM、选中元素等上下文；
- Claude Code 的本地 MCP 配置和权限策略；
- 计划使用的第三方 MCP 工具的官方仓库、版本、许可证和维护状态；
- 成功标准：从错误出现到定位文件、生成修复、测试通过分别允许多长时间。
